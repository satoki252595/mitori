# 13. 未解決の問い <!-- b_yq5pez2g -->

- **レビュー内部基盤**：`Session` と daemon の寿命管理が相互に参照し合う循環は意図した設計か、分離の方向性はあるか。 <!-- b_sg1n8yxj -->

- **コメント管理**：`CritJSON` をはじめとする型を別名で再公開し共有し続ける理由は何か、直接使う形にしないのは意図的か。 <!-- b_r0h6vk04 -->

- **レビューセッション管理**：旧側コメントのアンカーをベース参照から取る扱いと、ベース切替時にコメント付きファイルを孤児として残す扱いは、全ての版管理と範囲指定および削除記録との整合を含めて意図通りか。 <!-- b_5pjh45k5 -->

- **変更連携基盤**：full-stack 層での投稿停止と解決済み注釈への編集の投稿除外は仕様か、層切替を促す一時的制限か。 <!-- b_8ydtzww3 -->

- **設定と共有と live 中継**：`DefaultShareURL` が二箇所にある場合の正本はどちらか、`ShareURL` と `ShareTargets` が両方ある場合の優先順位はどうなるか、`LiveCookieFile` を項目設定から読む例外は意図的か。 <!-- b_evww2z70 -->

- **ブラウザ批評画面群**：共有層と主制御、ライブ画面と主制御の相互参照は意図した構造か、分離の方向性はあるか。 <!-- b_c65sbq5b -->

- **版管理抽象と差分取得**：`Sapling` と `Jujutsu` を待機域なしとして扱い、既定枝の上書きを自動検出より優先する理由と `Sapling` の `DefaultBaseRef` が既定枝をそのまま返す理由は何か、`RemoteFiles` が変更要求と `GitLab` の `layer` 差分のみを `forge API` 経由にする範囲は意図どおりか。 <!-- b_wr25rpt4 -->

- **plan 審査と daemon 管理**：`SessionKey` が `args` 空の時だけ `branch` を混ぜるのは互換維持のためか、意図した仕様か。 <!-- b_tgnengk5 -->

- **plan 審査と daemon 管理**：`DaemonHasBrowser` が到達不能時に `true` を返す安全側への倒し方は意図どおりか。 <!-- b_2w33wdhs -->

- **共有画面部品群**：非 JSON 応答で `fetchJSON` が空値を返す振る舞いは意図した仕様か、誤応答と空応答をどう区別すべきか。 <!-- b_hj4wbppf -->

- **コメント管理**：絞り込めないときに全件を返す場合と複数一致を誤りとする場合の使い分けは意図的か。 <!-- b_5w8527nh -->

- **CLI 入口と統合管理**：物語の欠落を自動修復する運用は意図したものか、厳密に拒否すべき場合はあるか。 <!-- b_nnzyqye5 -->

- **レビュー用 HTTP サーバ**：`consentNeeded` が設定済みか否かで二経路に分かれるのは移行期の扱いか、恒久の仕様か。 <!-- b_11r34rxq -->

- **設計判断**：単一 `binary` 構成で `frontend` 更新時の不整合をどう避ける想定か。 <!-- b_k4erda7t -->

- **非機能**：`prMetadataCache` の `cap` と遠隔内容の `bytesLRU` 容量、待機系の `timeout` と `stopWait` の値はどのように決まり、稼働監視は /api/health と `CRIT_DEBUG` のみで足りる想定か。 <!-- b_4y9gpr1y -->
