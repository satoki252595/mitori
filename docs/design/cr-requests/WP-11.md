## #1 The CLI process needs `@mitori/loop` (Pull helpers, MCP catalogue, review fixed lines)
- contract: `packages/core/src/domain.ts` §19 `PACKAGE_DEPS["@mitori/cli"]` (today: core, platform, client, server)
- change: add `"@mitori/loop"` (and `"@mitori/agent"` for `UNTRUSTED_FENCE`, or move `UNTRUSTED_FENCE` to core), and let
  loop `mcp/index.ts` export the catalogue rendering it already has:
  ```ts
  /** `tools/list` result rendered from MCP_TOOLS (readOnlyHint only; byte-fixed, fixtures/golden/mcp/tools-list.json). */
  export function mcpToolsList(): { tools: { name: string; description: string; inputSchema: object; annotations: { readOnlyHint: boolean } }[] };
  ```
  Alternative with the same effect: move loop C9 (`TouchHookInput`, `TOUCH_LIMITS`, `PULL_EXIT`, `parseTouchHook`,
  `agentLabelFromEnv`), C10 (`MCP_INSTRUCTIONS`, `MCP_LIMITS`, `MCP_TOOLS`) and the C2 constants the CLI prints
  (`REVIEW_STDOUT`, `REVIEW_EXIT`, `REVIEW_WAIT`) to `@mitori/client` (isomorphic, already a CLI dependency).
- why: these names are consumed in the CLI process, never in the daemon: the PostToolUse hook parses stdin
  (`mitori touch`), the MCP shim answers `initialize` / `tools/list` without the daemon (spec §10.8, ≤ 60 ms), and
  `mitori review` prints the shutdown / pending text when the daemon is gone (§10.1). With the current table the CLI
  can import none of them (type-only imports included), so the contract says "loop" while the only consumer cannot
  reach it. The binary size does not change (the CLI bundles server → loop already).
- also affected: CLI-U-007 wants `mitori check` to validate in-process without a daemon; the validators are gen's
  (`createLineValidator`, session `check`). Either add `@mitori/gen` too or amend CLI-U-007 to "through the daemon"
  (what the CLI does now: it starts the daemon when needed, ≈ 150 ms).
- workaround in place: `apps/cli/src/commands/loop-contract.ts` (copies of the C2/C9/C10 names + `UNTRUSTED_FENCE`
  parts + the copy-mode preamble) and `apps/cli/src/commands/mcp/tools-list.ts` (the rendered catalogue). They are
  kept identical by tests on both sides against the same fixtures: `fixtures/golden/pull/hook-cases.json`
  (`packages/loop/src/pull/pull.test.ts` ↔ `apps/cli/src/commands/loop-contract.test.ts`) and
  `fixtures/golden/mcp/tools-list.json` (`packages/loop/src/mcp/mcp.golden.test.ts` ↔ the same CLI test). The
  version table of server `decideVersionAction` is re-stated in `daemon-client.ts` `versionAction` (importing
  `@mitori/server` from a client command would evaluate the whole daemon graph and cost the `touch` / `mcp` start-up
  budgets); a test compares both tables.
- urgency: before WP-16 (codex adapter) adds more CLI-side Pull code; the copies are the drift risk.

## #2 `Installer.plan` / `install` cannot name the project for `scope: "project"` and `agents-md`
- contract: `packages/loop/src/contract.ts` C11 `Installer`
- change:
  ```ts
  plan(target, scope, opts: { mcp: boolean; project?: { root: string; docDir: string } }): IntegrationFile[];
  install(target, scope, opts: { mcp: boolean; force: boolean; project?: { root: string; docDir: string } }): Promise<…>;
  ```
  (`project` required when `scope === "project"` or `target === "agents-md"`; `docDir` renders `{docDir}` of the
  AGENTS block; an absolute docDir = shadow workspace ⇒ `E_PRECONDITION`, spec §11.3.)
- why: `createInstaller` is global (CONS-22) and the options carry no repository, yet project installs write
  `<repo>/.claude/skills/…` / `<repo>/AGENTS.md` and the block embeds the workspace's docDir.
- workaround in place: `packages/loop/src/install/installer.ts` `InstallOptions` reads `project` from the same
  options object (callers build it in a variable; an object literal would fail the excess-property check).
- urgency: blocks `mitori install … --scope project` / `install agents-md` end to end (with #5).

## #3 Integration template sizes vs the budgets (`install.agentsTokens`, `install.skillBytes`)
- contract: `packages/loop/src/contract.ts` `INTEGRATION_TEMPLATES` (byte-exact text)

  (83 without; claude-v5 `markdown_en`, `estimateTokensRaw`) against the 80-token limit. Candidates (same meaning):
  - 78 tokens: ``mitori: design doc at `{docDir}/README.md` (may lag code). Run `mitori review` only when asked; reply via `mitori reply`. Edit `{docDir}/` only in `tmp/prep/*/out/` per a prep README.``
  - 71 tokens: ``mitori: design doc `{docDir}/README.md` (may lag code). `mitori review` only when asked; reply via `mitori reply`. Never edit `{docDir}/` except prep `out/` files.``
  Plugin `SKILL.md` is 1,512 B (project 1,519 B, codex 1,305 B): within AC-L77's 1.5 KB (1,536 B) but over

  Please state which (the test checks whole file ≤ 1,536 B and body ≤ 1,400 B). `marketplace.json@1` has no

- why: budgets are part of correctness; the template is contract text, so WP-11 cannot fix it.
- workaround in place: `packages/loop/src/install/install.golden.test.ts` marks `install.agentsTokens` as

## #8 Idle check for the version restart, and a detached spawn
- contract: `packages/core/src/api.ts` `DaemonStatus`; platform `SpawnSpec`
- change: `DaemonStatus.idle: boolean` (no job, no waiting `mitori review`, no generation — the server's own
  definition), and a platform option to start a detached child with stdio ignored (`SpawnSpec.detached?: true`).
- why: the CLI approximates "idle" with `scheduler.running + queued === 0` (a waiting `mitori review` is not visible
  in `GET /daemon`, so a version restart could cut it — it then exits 10 and the agent re-runs NEXT). The headless
  daemon is started with `processGroup: true`; its stdout/stderr stay pipes to the exiting CLI, so `_serve
  --detached` must never write to stdio.
- workaround in place: `daemon-client.ts` `idle()`; `process-io.ts` `spawnDaemon` + `run.ts` `--detached`.
- urgency: nice to have.
