## SEC-05 for GitReader reads (FYI, no contract change)
- contract: core `GitReader` doc comment (§18) — mention it
- change: `status()` / `statusDirty()` always run with `-c filter.<x>.{clean,smudge,process}= -c filter.<x>.required=false`
  for every filter driver defined in repo-local / worktree config (`git config --list --show-scope --includes`, cached
  by the config mtimes). Verified: plain `git status` executes a planted `filter.evil.clean` on a stat-dirty file
  (`git.int.test.ts` "SEC-05"). User/global config (e.g. git-lfs) stays active. The other reads (`ls-files`,
  `check-attr`, `cat-file --batch`, `diff-tree --name-only`, `log --name-only`, `rev-list`) execute no repo commands;
  fsmonitor is off and `--no-pager` is set for all of them.
- addendum (verifier pass): in a **partial clone** any read that needs a missing object (`cat-file --batch` of an old
  blob, `log` in a treeless clone) lazy-fetches from the promisor remote — network from a read, and a repo-local
  `core.sshCommand` was executed (verified with a planted command). Every read now runs with `GIT_NO_LAZY_FETCH=1`
  (git ≥ 2.44) and `-c protocol.allow=never` (older git: "transport not allowed" before any command runs); such an
  object is `E_NOT_FOUND`. Suggest loop's `GIT_ENV` adds `GIT_NO_LAZY_FETCH=1` too (its `GIT_BASE_ARGS` still allow
  https, so a snapshot/diff in a partial clone over https would fetch from the network mid-job).
- addendum 2 (verifier pass): the `-c` neutralizers were evadable — a driver named `a=b` (`[filter "a=b"]`,
  `filter=a=b` in .gitattributes) ran, because `-c filter.a=b.clean=` is split at the first `=`. The overrides now
  also go as `GIT_CONFIG_COUNT` / `GIT_CONFIG_KEY_<n>` / `GIT_CONFIG_VALUE_<n>` (git ≥ 2.31). The cache also missed
  drivers added to an `include.path` file (now re-read whenever includes exist) and, in a linked worktree, any change
  of the main repository's config (the key now stats the common dir's `config`). **Loop's `GIT_COMMAND_CONFIG_PATTERNS`
  neutralizers (`-c <key>=`) have the same `=` problem** for every subsection-bearing key (`filter.<x>.*`,
  `merge.<x>.driver`, `diff.<x>.command|textconv`): WP-08b should pass them through `GIT_CONFIG_*` env as well.
- why: the indexer calls `statusDirty()` on workspace open, before any trust decision (loop's
  `GIT_COMMAND_CONFIG_PATTERNS` + TrustRecord `git_config` cover mitori's write-side git calls).
- urgency: none for platform (implemented); the loop notes above before WP-08b lands.

## Watcher: a vanished directory arrives as `delete <dir>`
- contract: indexer `FsChange` doc comment / indexer spec §10.2 step 1–3 (indexer, WP-02)
- change: say that a `delete` whose path is not a file in the index but a directory prefix of indexed files means
  "everything under `<path>/` is gone" (the indexer drops those entries; rename detection still pairs them with the
  `add`s of the same batch by blob).
- why: `mv a b` (IDE folder move) and moving a directory out of the tree are reported by FSEvents and inotify as ONE
  event for the directory; its files were never listed by the watcher (only files touched since the watch started are
  known). Verified: `mv a b` → `[delete a, add b/deep/f0.ts, add b/deep/f1.ts, …]` in one batch
  (`watch.int.test.ts` "a directory rename"). Without the rule the old paths stay in the index until the next warm
  scan. Alternatives rejected: a `{kind:"git"}` warm scan for every unknown deleted path costs ≈ 25 ms on ordinary
  saves (editor backup files `x~` are created and removed inside one batch); listing every directory at watch start
  costs setup time and memory for trees the watcher does not otherwise need.
- workaround in place: none in platform (the event shape is already as proposed).
- urgency: before WP-02 implements `update()`.
