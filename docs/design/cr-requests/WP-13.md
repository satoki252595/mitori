# WP-13 — contract change requests (self-contained HTML export)

Raised while finishing WP-13 on `fin/export`. Each item names the workaround that is in the code (`CR-PENDING(WP-13)` or the
mentioned file) and what the architect should decide. Nothing in `packages/core` was changed.

## 1. `createHtmlExporter` needs the code side — optional `source` dep
- contract: `packages/doc/src/contract.ts` — `createHtmlExporter` (declared in `packages/doc/src/export/index.ts`), `HtmlExporter`
- change (applied locally as an OPTIONAL dep, so the frozen call sites keep compiling):
  ```ts
  createHtmlExporter(deps: { doc; renderer; layouter; secrets; viewerAssets; clock;
    /** NEW */ source?: ExportSource });
  interface ExportSource {
    file(path: RepoPath): Promise<{ text: string; blob: GitOid; lang: SourceLang } | null>; // cite peeks
    symbol?(path, start, end): SymbolKey | undefined;                                       // peek header
    head?(): string | null;                                                                 // band + header HEAD
    modules?(): MapView["modules"];                                                          // room sizes of the map
    mapDiagram?(): DiagramIR | null;                                                         // map of a doc without its own container diagram
  }
  ```
- why: the frozen deps give the exporter a `DocStore`, a renderer, a layouter and a scanner — no way to read the cited code. The
  spec (ux §4.13) wants a static peek with ±3 lines per cite, `ExportRes.codeExcerpts` and `excerpts: false`; without a port the
  exporter could only write `path:line`. `@mitori/doc` must not do file I/O (CR m1-7 / CONS-07), so the composition root supplies it
  (`packages/server/src/wiring/export.ts` `exportSource(indexer)`: only indexed, non-excluded files, ≤ 2 MB, so deny-globbed secret
  files are never read).
- workaround in place: `source?` is optional; absent ⇒ no excerpts, no module sizes, HEAD from the manifest. `ExportSource`/`ExportFile`
  are exported from `packages/doc/src/export/index.ts` (INDEX.md changes accordingly).
- urgency: blocks the `@export` acceptance (cite peek).

## 2. `ExportPayload` (doc) must stay equal to `ViewerPayload` (web §16)
- contract: `packages/doc/src/export/payload.ts` `ExportPayload` ↔ `apps/web/src/contract.ts` `ViewerPayload`
- change: none to the shapes. `@mitori/doc` cannot import `apps/web`, so `ExportPayload` mirrors the type; `e2e/export/payload-contract.test.ts`
  fails to compile when the two drift (mutual assignability). Proposal: move the one interface to `@mitori/core` (`api.ts`) when the next
  batch opens, and delete the mirror.
- urgency: nice to have.

## 3. `GET /ws/:ws/export/html` has no `decisions` query
- contract: `packages/core/src/api.ts` — `ApiRoutes["GET /ws/:ws/export/html"]` query `{ level?, lang?, excerpts? }`
- change: add `decisions?: "0" | "1"` (the `POST` body has `includeDecisions`; the GET download — what the app's export dialog uses —
  cannot ask for it).
- workaround: the GET route always passes `includeDecisions: false` (the privacy-conscious default; the CLI/POST can include them).

## 4. `includeDecisions` only controls the decisions LIST
- `DocStore` has no reader for `decisions/<id>.md` (doc does no file I/O), so "include resolved decisions" can only mean the
  `s10:decisions` list block of §10 (title, date, related block). The decision records' own text (thread quotes, verbatim) is NEVER
  embedded. Please confirm that is the intended reading of ux §4.13 "決定事項を含める", or add `DocStore.decisionText(id)`.

## 5. `DocStore.mdLine` is still a stub (CR m1-46)
- `BlockView.mdLine` / `data-ln` is 0 in an export (the viewer has no permalinks to a repo). The exporter tolerates the stub
  (`try/catch` → 0, marked `CR-PENDING(WP-04)` in payload.ts); no action needed from WP-13 once WP-04 lands it.

## 6. `ExportReq.lang` is the language of the CHROME, not of the text
- The viewer's `uiLang`. Block text stays in the doc's language (`BlockView.htmlLang`); translations (D5) are not exported. The export
  dialog should say so (「画面の言語。本文は書かれた言語のまま」).
