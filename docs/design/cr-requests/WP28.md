# WP28 — change requests (vendor CLI auto-follow, 2026-10-13)

## #1 `BinaryPin.by: "auto-update"` + `previousVersion?`, `EngineStatus.followed?`
- contract: `packages/core/src/domain.ts` — `BinaryPin`; `packages/core/src/api.ts` — `EngineStatus`
- change:
  ```ts
  // domain.ts
  by?: "first-run" | "user" | "auto-update";
  previousVersion?: string; // set only when by === "auto-update"
  // api.ts
  followed?: { from: string; to: string; at: Iso8601 }; // latest auto-follow notice
  ```
- why: vendor CLIs (Claude symlink swap, Muse versioned binary swap, Codex update) change the pinned
  executable without human action. The daemon may follow the update only through the approved entry
  (saved `pin.path` re-resolved, or the Muse `.muse-version` marker in the same directory) after
  re-checking SEC-10 path safety, ownership/mode (POSIX), `--version` (same limits as `setup-pin`
  `prepareProviderPin`), and the engine capability gate (Claude `--help`, Codex `CODEX_VERSION`,
  Muse text-only argv + config). The card needs the old→new versions: pins carry `previousVersion`,
  and Muse (no pin) carries its last follow in `EngineStatus.followed` (memory only; the daemon log
  keeps the durable line). All fields are optional additions; existing readers are unaffected.
- workaround in place: none (new behavior; detect keeps returning `E_ENGINE_BINARY_CHANGED` /
  `E_AGENT_NOT_INSTALLED` / `E_AGENT_CAPABILITY` until the follow logic lands).
- urgency: blocks WP28 acceptance (auto-follow + 「旧版→新版」 notice).
