## B. Decisions the spec left open (kept; flip if you disagree)

1. **Wilson z is 1.645 (one-sided 95 %), not 1.96.** The gate asks whether the data rules out a true rate below `threshold − 10 pp`.
   The acceptance example (n = 30, p = 0.75, threshold 0.70 passes) has a lower bound of 0.603 against the 0.60 gate with
   z = 1.645 and 0.573 with z = 1.96, so only the one-sided value is consistent with it. Consequence: 23 of 30 passes a 70 %
   threshold, 22 of 30 does not, two runs of 22/30 pooled (44/60) do. `minN` defaults to 30; below it the verdict is
   `insufficient`, never `pass`. Please mention z in testing spec §7.4 / SC-14.
2. **Static initial-JS check vs the route-specific one.** `bun run size` measures what the shell's HTML requests (module scripts +
   `modulepreload`, br and gzip bodies from a real server, decimal KB). The spec's "larger of map / Reader route at
   `mitori:map:painted`" needs a browser: `e2e/harness/metrics.ts#initialJs(page, url, until)` does that (Playwright
   `request.sizes().responseBodySize`), and WP-10a's `@wp10a` spec should call it and assert `expectWithinBudget("asset.js.initial.gz", …)`.
3. **R1 SC-21 is honoured**: until M3 only `asset.js.initial.gz` (150 KB), `asset.css.gz` (25 KB) and `asset.font` (0) fail `size`;
   chunk limits, the initial-JS target and `asset.precompressed` are warnings. `--strict` turns every limit into a failure (use it from M3).
4. **Machine factor.** The calibration workload leaves out the tree-sitter wasm parse of the spec (the grammar loader is the indexer's);
   it is xxh3 over 64 MiB, SQLite inserts, JSON and plain JS (≈ 0.3 s). `bench/runner/reference.json` was recorded on the maintainer
   machine (Apple M5 Max, best of 5). Re-record with `bun bench/runner/run.ts --record-reference` after adding a part.
5. **File placement** (MILESTONES §1.2 over the spec's file names): `bench/run.ts` → `bench/runner/run.ts`, `bench/compare.ts` →
   `bench/compare/compare.ts`, `bench/assets.ts` (`assets:check`) → `bench/asset/size.ts` (`bun run size`), calibration → testkit
   `perf/calib.ts`, `e2e/playwright.config.ts` → `e2e/harness/playwright.config.ts`. Results of local runs go to
   `bench/results/<sha12>.local.json` (already git-ignored); reports of `eval` to `eval/reports/<day>-<sha12>-<tier>/`.
6. **Where the daemon is started from.** `startTestDaemon` runs `bun --preload packages/testkit/src/server/test-flag.ts
   apps/cli/src/main.ts <repo> --no-open` (or `_serve`), reads the URL line, and treats a `#fragment` as the login nonce/token. The
   walking skeleton has neither a token nor `/__test/*`: `token` is `""`, `metrics()` returns `{}`, the cassette switch
   (`POST /__test/engine`) is skipped on 404. WP-09 / WP-INT make these exact; the signature does not change.

7. **`bin.startup`** is checked by `bun run size` (the budgets' `measure` points at `bench/asset/size.ts#bin-startup`): 20 spawns of
   `dist/mitori-<host> --version` after one discarded run (hyperfine is not required), the median against 20 / 50 ms. Being a time
   budget it only fails on the reference machine; the calibration runs lazily, only when the median is over the limit.
8. **`bench:compare --asset`** adds the served-bytes table with a Δ column against base (head's `size.ts --tree <side>` on both
   trees) and lets head's hard asset limits fail the comparison; the PR job should pass it. **`--no-wait`** skips the quiet-machine wait.
9. **Chrome trace categories.** testing spec §6.6 lists `devtools.timeline`, `blink.user_timing`, `v8.execute`; on Chromium 153 `RunTask`
   (long tasks) needs `disabled-by-default-devtools.timeline` and the JS stack of a forced layout needs
   `disabled-by-default-devtools.timeline.stack` (`e2e/harness/trace.ts`).
10. **Rate SLO rows are red when the Wilson bound misses the limit itself** (`eval/slo.ts`). SC-14's "Wilson 下限 ≥ 閾値 − 10pp" reads
   閾値 = the pass threshold (= the budget's target), and the n = 30 budgets already sit their limit 10 pp below the target
   (`quality.patch.*` 70 / 60, 85 / 75; MILESTONES M3 "Wilson 下限 ≥ 60%"). Taking the margin off the limit again (the first version
   did) let 22 / 30 through as yellow although `judgeRate(22/30, 0.7)` fails. Green / yellow is the point estimate against the
   target. Please state in testing spec §7.4 that the margin is already inside the n = 30 limits.
11. **Time budgets in e2e gate only in the `perf` project on the reference machine** (`checkBudget` / `expectWithinBudget`, §5.2 and
   §6.8); structural ones (DOM, code lines, bytes, CLS, heap) gate in every project. `bun run e2e --project perf` measures the machine
   factor (Bun) and passes it to the Node workers as `MITORI_MACHINE_FACTOR`.
12. **`agent.spawns.real` is counted by the preload** (the budget's `measure`): a per-run copy of the spawn guard records each hit next
   to its shims (PATH is the only variable the product's env allowlist keeps), and the preload's `afterAll` fails the run when there is
   one. Once `[test] preload` is on (A.1), a test that reaches `claude` / `codex` without `MITORI_LIVE=1` fails the run even if it
   swallowed the exit 97. The current suite has 0 hits.
13. **Metered eval money**: a run billed outside the subscription window is capped by min(tier / weekly cap, `--approve-metered-usd`,
   $6 − metered spend of the current UTC month from `eval/reports/*/summary.json`); a used-up month exits 3.

## C. Contract gaps (testkit/contract.ts is architect-owned)

1. **`BudgetEntry` has no `minN`** although ARCHITECTURE §10.1 lists `minN?` and `bench/budgets/*.json` carries it (the lint accepts
   it). `budget()` returns the stored entry, so `minN` is there at runtime; the eval harness reads it through a local widening
   cast (`eval/slo.ts`). Proposal: add `minN?: number` to `BudgetEntry`.
2. **`TestHome.env`** documents "env to pass to spawned mitori processes". It holds overrides only (MITORI_HOME, MITORI_TEST,
   MITORI_TEST_SEED, git identity/clock, TZ, LANG/LC_ALL, guarded PATH) — merge it over `process.env`. No contract change.
3. **`PageLike`** is `{ goto }`; the helpers need `evaluate` (and CDP for throttling / IME). They narrow at runtime and throw
   `E_INVALID_INPUT` for a bare `{ goto }`. A real Playwright page satisfies everything.

## D. For other owners (no CR needed)

- **testkit under Node.** Playwright runs specs under Node, which loads `@mitori/testkit`'s whole export graph. Anything in testkit
  must therefore avoid `import.meta.dir` and static `bun:*` imports (use `fileURLToPath(new URL(…, import.meta.url))` and
  `await import("bun:sqlite")` inside functions). `fixtures/spec.ts` was the one offender and is fixed.
- **The daemon's CSP forbids inline scripts**, so e2e specs that need a scripted fixture page use `page.evaluate` (CDP) or a routed
  origin, not `page.setContent("<script>…")`.
- **`bun run size`** runs WP-11a's binary gate first and then this WP's served-bytes gate; both need the web build under
  `dist/.build` (the skeleton test or `build:bin` creates it). Flags go to both: `bun run size --dist <dir> --strict`.
