# WP-06 — change requests (gen, 2026-10-03)

> **Answered in CR batch 2 (2026-10-03)** — decisions in `packages/core/CR-LEDGER.md` §5 (CR m1-1 … CR m1-121). Append new requests below this line.

Requests found while implementing `packages/gen` (planner, prompts, line protocol, Verifier, orchestrator,
session engine). Each local workaround is marked `CR-PENDING(WP-06)` in the code.

## R1 Audience in `ASPECT_DEFAULTS` (compact line form)
- contract: `packages/doc/src/contract.ts` — `ASPECT_DEFAULTS`
- change: `{ kinds, depth, audience: readonly Audience[] }` per aspect, e.g. `tldr: { kinds: ["prose"], depth: "L0", audience: ["newcomer", "pm", "dev"] }`.
- why: PT-03 / gen.ts `GenBlockLine` say kind, depth and audience are derived server-side from `ASPECT_DEFAULTS`, but it
  has no audience. The values are the per-prompt "Audience" rules of gen spec §5.6.
- workaround in place: `ASPECT_AUDIENCE` in `packages/gen/src/line/aspects.ts`.
- urgency: nice to have (behaviour is correct; one table instead of two).

## R2 `GEN_PROMPTS[*].form` for the gen.* block prompts
- contract: `packages/gen/src/contract.ts` — `GEN_PROMPTS`
- change: `form: "compact"` for gen.module / parent / overview / flows / datamodel / quality / decisions / risks /
  deepdive (labels, glossary, questions have no block lines; keep `"full"` or use `"compact"` too).
- why: R1 (PT-03, ADR-0011 R1-3) makes the compact form the default; the table still says `"full"`, which would require
  kind / depth / audience on every line (V03).
- workaround in place: `lineForm()` in `packages/gen/src/prompts/context.ts` validates gen.* prompts as compact (the
  compact validator also accepts full-form lines).
- urgency: before M-1 (the M-1 comparison flips this per prompt).

## R3 Public factories of the gen internals the server must wire
- contract: `packages/gen/src/contract.ts` (+ sub-directory `index.ts` exports)
- change:
  ```ts
  export function createPromptRenderer(deps: { hasher: Hasher; secrets: SecretScanner; indexer: Indexer; salt: () => string }): PromptRenderer; // prompts/
  export function createVerifier(deps: { indexer: Indexer; anchors: AnchorEngine; hasher: Hasher; clock: Clock; metrics?: Metrics }): Verifier & ClaimStamper; // verify/
  export function createSchedulerGenEngine(id: "claude-cli" | "anthropic-api", scheduler: AgentScheduler, ctx: { ws: WorkspaceKey; sandboxCwd: string }): GenEngine; // engines/
  export function genSalt(db: SqlDb, random: Random): string; // orchestrator/ (gen_meta salt for the renderer)
  ```
  and document on `PromptRenderer` that `render()` uses the system prompt last rendered by `system()` for the same
  (system id, lang, workdir) — that is how a run pins its system prompt + repo pack (PT-05).
- why: `GenDeps.prompts` / `GenDeps.engines` are required inputs but the composition root cannot build them, and the
  doc store needs the Verifier as its `ClaimStamper` (CONS-06). Adding exports changes `briefs/INDEX.md`, so it is a CR.
- workaround in place: the implementations exist (`prompts/renderer.ts`, `verify/verifier.ts`,
  `engines/scheduler-engine.ts`); `createGen` falls back to the scheduler adapter when `GenDeps.engines` lacks an engine;
  `createGenInternal` (orchestrator/gen.ts) exposes the Verifier.
- urgency: blocks WP-INT wiring of gen.

## R4 `GenCallResult.continuations` and `GenCallResult.error`
- contract: `packages/gen/src/contract.ts` — `GenCallResult`
- change: `continuations?: number` (PT-09: CLI-internal continuations ⇒ no mitori retry, excluded from the EMA) and

- urgency: nice to have (adapters already set the fields).

## R5 A file reader in `GenDeps` (session ingest / `mitori check`)
- contract: `packages/gen/src/contract.ts` — `GenDeps`
- change: `fs: FsReader` (core port; lstat to refuse symlinked `out/` files, GEN-I-055).
- why: `SessionEngine.ingest` / `check` read `<docDir>/tmp/prep/<id>/out/*.ndjson` (api `IngestReq`: "the server reads
  out/ from disk"), but GenDeps has no reader.
- workaround in place: `GenDepsExt = GenDeps & { fs?: FsReader }` (orchestrator/gen.ts); without it ingest / check fail
  with `E_UNSUPPORTED`.
- urgency: blocks the session engine in the daemon.

## R6 Cache key subject (§3.8 R1, AC-28)
- contract: core `GenTask.cacheKey` doc comment; gen spec §3.8
- change: state that `xxh3(userBytes)` is taken over the SUBJECT bytes — the user message rendered without the target's
  own current content (EXISTING, CHANGES, EXISTING_FLOWS and the gen.regen addendum) — and that both addendum versions
  (gen.regen, gen.retry) are always part of the key.
- why: with the literal formula a second run over unchanged inputs never hits the cache, because every task of the
  second run sees its own first-run blocks in EXISTING (AC-28 / GEN-U-042 "全 task cached" would be impossible). Replays
  go through the same apply path with the stored idMap, so they are no-ops on an unchanged doc.
- workaround in place: implemented as above in `packages/gen/src/prompts/renderer.ts`; the early overview is skipped
  once s0–s2 have AI content (it only exists to give a fresh doc its first block quickly).
- urgency: spec / comment wording only.

## R12 A calendar-month usage range (anthropic-api `monthlyCapUsd`)
- contract: core `UsageRange` / agent `UsageLedger.summary`
- change: `UsageRange += "month"` (calendar month in the daemon's time zone), or `UsageLedger.monthToDate(engine)`.
- why: gen spec §8.3 checks "今月 $a + この run $b ≤ 上限 $c" before an anthropic-api run starts; the ledger only offers
  rolling ranges (`today`, `7d`, `30d`, `all`), and `byDay` totals are not split by engine.
- workaround in place: `Runner.checkMonthlyCap` uses `summary("30d").byEngine["anthropic-api"]` (conservative: it can
  refuse a run the calendar month would still allow; the agent's ledger keeps enforcing the cap per call).
- urgency: before anthropic-api is offered in the UI.

## R13 `PrepInfo.expiresAt` wording vs per-task drift (§8.4.3)
- contract: core api `PrepInfo.expiresAt` comment ("index digest change also expires it")
- change: "expires after 24 h; a task whose inputs changed since prep is refused at ingest (drift) and prepared again by
  `prep --continue`".
- why: gen spec §8.4.3-3 / AC-23 refuse only the drifted tasks; expiring the whole packet on any index change (any saved
  file) would throw away the agent's finished work for unrelated edits.
- workaround in place: none needed (the implementation follows §8.4.3).
- urgency: wording only.
