## 1. Worker protocol: three optional fields and one status the Worker already sends
- contract: `packages/indexer/src/contract.ts` §H — `ParseItem`, `ParseItemResult`
- change:
  ```ts
  interface ParseItem { /* … */ skipContentRules?: boolean }            // R03 include: skip R11–R13
  // ParseItemResult, status "ok", add:
  chars: number;                    // UTF-16 length (FileEntry.tokensEst without re-reading the file)
  lang: SourceLang;                 // language actually used (shebang refines `generic`)
  grammar: GrammarId | null;        // grammar actually used (Flow ⇒ tsx)
  skeleton?: { l0: string; sig: string; doc: string };   // fragment bodies without the path-bound header line
  // new member of the union:
  | { status: "unreadable"; path: RepoPath }            // vanished / EACCES between stat and read (R00 special)
  ```
- why: skeleton fragments are content-addressed (`blob × extractor × tier`, spec §7.5) and need the text, which only
  the Worker has during S1 (re-reading every file on the main thread would double S1 I/O); `Indexer.skeleton()` is
  synchronous, so the fragments must exist before it is called. `chars` / `lang` / `grammar` avoid a second read;
  `unreadable` has no rule id among R11–R13.
- workaround in place: `packages/indexer/src/parse/protocol.ts` (`ParseItemExt`, `ParseOkResult`, `ParseUnreadable`);
  structured clone carries the fields through any worker entry unchanged.
- urgency: nice to have (no behaviour depends on the contract text), but the server's worker entry must not strip them.

## 3. GitReader gaps seen from S0 / update()
- contract: `packages/core/src/domain.ts` §18 — `GitReader`
- change:
  ```ts
  /** `git check-ignore -z --stdin` (spec §10.1: new untracked paths of a watcher batch). */
  checkIgnore(paths: readonly RepoPath[]): Promise<RepoPath[]>;
  /** `git ls-files -z --others --ignored --exclude-standard --directory` (optional: lets S0 list gitignored entries). */
  lsIgnored?(): Promise<RepoPath[]>;
  ```
- why: (a) `update()` cannot tell whether a brand-new path is ignored; it is indexed as untracked until the next warm
  scan. (b) `fixtures/truth/nongit.json` lists `node_modules/`, `.venv/`, `build/` entries as `ignored / gitignored`,
  but nothing in the port enumerates ignored files, so `excluded: "gitignored"` can never be produced (the nongit
  `files` score misses those three; IDX-AT-05 itself — "not enumerated" — passes).
- workaround in place: `packages/indexer/src/update/incremental.ts` (new paths = untracked, not ignored).
- note for WP-01: one `git ls-files -s -z --cached --others --exclude-standard` process returns both lists (untracked
  entries come back without the `<mode> <oid> <stage>\t` prefix) — halves the spawns of the warm path. On a shadow
  repo with 12k files that listing alone costs ≈ 33 ms; `idx.warm.rescan.7k` (25 / 50 ms) needs the platform to
  avoid it (e.g. a stat walk of the previous path set when no directory mtime changed, spec §10.1-B).
- urgency: (a) nice to have; (b) needed only if the nongit truth keeps the gitignored rows.

## 7. Server worker entry (packages/server/src/workers/parse.ts) — recommendations, no contract change
- Run a full GC (`Bun.gc(true)`) after every ~4 MiB of parsed source: a parse batch leaves ≈ 10× its size of
  short-lived objects (query matches) and JSC lets them grow to hundreds of MB per Worker before collecting
  (`packages/indexer/src/parse/test/worker-entry.ts` does this).
- The pool is created early on cold scans: `ParsePool.prewarm(n, grammars)` spawns Workers from the `ls-files`
  listing and sends one zero-byte item per grammar so the queries compile while S0 stats.

Warm counters (`idx.warm.parseCalls / filesHashed / sqlWrites`) are 0 on every repo. Of crit's warm rescan, the git
subprocesses take 9–14 ms on this machine (`ls-files` + `rev-parse`), the indexer ≈ 4–6 ms. On the same machine W = 2
gives 10.9 MB/s of parse per Worker, W = 6 only 6.2 MB/s (the P-cores are shared with the other agents' processes),
so the per-repo numbers above are upper bounds for an idle reference machine.

Per Worker the cost is ≈ 150–220 ms CPU per MB (tree-sitter parse ≈ 55 %, query marshaling + extraction ≈ 45 %)
plus ≈ 80 ms of cold start (spawn, grammar load, query compile, JIT); `W = ceil(MB / 0.75)` capped at
`perfCores` (6) leaves gostd's 45.7 MB of parse targets at ≈ 7 s CPU / 6. O-IDX-1 (fit the coefficients) is the place
to revisit the cap; the measurements were taken on a loaded machine and should be redone in a WP-12 measurement window.
