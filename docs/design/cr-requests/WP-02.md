- contract: `packages/indexer/src/contract.ts` §H — `ParseItem`, `ParseItemResult`
- change:
  ```ts
  interface ParseItem { /* … */ skipContentRules?: boolean }            // R03 include: skip R11–R13
  // ParseItemResult, status "ok", add:
  chars: number;                    // UTF-16 length (FileEntry.tokensEst without re-reading the file)
  ```

  synchronous, so the fragments must exist before it is called. `chars` / `lang` / `grammar` avoid a second read;
  `unreadable` has no rule id among R11–R13.
- workaround in place: `packages/indexer/src/parse/protocol.ts` (`ParseItemExt`, `ParseOkResult`, `ParseUnreadable`);
  structured clone carries the fields through any worker entry unchanged.
- urgency: nice to have (no behaviour depends on the contract text), but the server's worker entry must not strip them.

## 6. Schema notes (idx@1 as shipped in `INDEXER_MIGRATIONS`, all additive to spec §9)
- `idx_files.raw` (on-disk spelling of NFD names), `idx_files.mtime_us` instead of `mtime_ns` (ns does not survive a
  JS-number round trip through `SqlDb`; the stat cache compares µs), `idx_blobs.chars / lang / grammar / note / data`
  (JSON of headings, rationale, fact candidates), `idx_symbols.decorators`, `idx_blob_text.bytes` nullable (a pin may
  arrive before the content). BLOB columns hold JSON, not deflate (O-IDX-12 open; `WriteQueue` callbacks are
  synchronous, `CompressionStream` is not).
- Pin store GC: rows with refcount 0, `last_ref_at` older than 7 days and a blob that no path currently has; run at
  most once a day from scan / update (no timer).
- A parse that hit the 250 ms budget (`note: "parse_timeout"`) is not written to `idx_blobs` / `idx_symbols` /
  `idx_skeleton`: the time budget depends on machine load, so the next daemon start parses the file again (within a
  process the fallback is reused, warm rescans stay cheap). `idx_files.note` still records it.
- Pin store on shadow workspaces: every file is untracked, so the background pinning after a scan stores a copy of
  every included text (gostd ≈ 47 MB in `idx_blob_text`, ≈ 0.7 s of background persistence). That is what R1 §7.7
  asks for ("dirty ファイルを hash した時点で内容を保存"); `pinBlobs()` additionally captures a current dirty text that
  is not stored yet, so an anchor made right after a scan survives the next save. If the copy is too large, the
  alternative is to store shadow texts only on `pinBlobs()` (anchors) — an architect decision.

## 7. Server worker entry (packages/server/src/workers/parse.ts) — recommendations, no contract change
- Run a full GC (`Bun.gc(true)`) once ≈ 256 KiB of source were parsed since the last one, after posting the batch's
  reply: a batch leaves ≈ 10× its size of short-lived objects (query matches) and JSC lets a Worker's heap reach
  ≈ 80 MB per 1 MiB batch before collecting. Measured at W = 6 (`packages/indexer/src/parse/test/worker-entry.ts`
  does this now): peak RSS react 1,038 → 722 MB, gostd 1,320 → 980–1,050 MB, crit 722 → 602–646 MB; wall time
  unchanged within noise (gostd +5 %). Every 4 MiB (the earlier recommendation) left react above the 1 GB limit.
- The pool is created early on cold scans: `ParsePool.prewarm(n, grammars)` spawns Workers from the `ls-files`
  listing and sends one zero-byte item per grammar with ≥ 5 % of the parse candidates, so their queries compile while
  S0 stats (rare grammars compile on the Workers that receive them).
- Per Worker: ≈ 40–50 MB once the grammars are compiled, WASM linear memory stays at its initial 32 MB on the corpus,
  JSC heap high-water ≈ 76 MB per 1 MiB batch before the GC above.

## 10. Behaviour the contract text does not spell out (verifier pass, 2026-10-03) — please confirm or amend the docs
- `SymbolEntry.signature` is secret-scanned when it contains a literal (`"` `'` `` ` `` `=`: parameter defaults such
  as `key = "AKIA…"`), like `doc` (core says "secret-scanned" for `doc` only). `sigHash` is computed from the raw text
  in the Worker and is unaffected; `symbolsAt()` (anchor, in-daemon) stays raw. Proposed core doc line for
  `signature`: "secret-scanned when it carries a literal".
- `symbolsAt(path, blob)` answers `[]` without reading anything when `path` is excluded (deny / secret included) or
  is a text-profile file (docs, data-like config) — the same classification `symbols(path)` uses; a deleted path is
  classified by name.
- `blobText()`'s last resort (the current file with that blob, read from disk) skips excluded files, and the unknown
  blob `""` answers null; `pinBlobs` / `unpinBlobs` ignore `""`.
- `skeletonHeader` flattens paths and import specifiers to one line (`\n` `\r` TAB U+2028/2029 → space, other C0 / DEL /
  NEL controls dropped); everything else in a skeleton is the source line as is.
- `scan()` and `update()` are serialized in call order (an `update()` waits for a running scan — spec §1.1 — and a
  `scan()` now also waits for a running update; a queued or running scan is still shared, `force` aborts it).
- `update()` decides deletions by stat, not by the event kind (an editor's rename-save reports `delete` for a file
  that exists again).
- Content keys (`idx_blobs.extractor`) gain `#d<8 hex>` once `FACT_DETECTORS` is non-empty (detector-set version;
  facts live in the S1 cache, spec §9 keys them by blob × detector set). Empty today, so no key changed.
