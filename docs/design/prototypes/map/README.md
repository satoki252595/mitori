# 見取り図ファースト（map-first spatial）UI プロトタイプ

- 対象: mitori の UI 方向性「MAP-FIRST SPATIAL」。ホームはリポジトリの間取り図で、部屋（モジュール群）を選ぶとその節が右のシートに開く。
- 成果物: `index.html`（単一ファイル。CSS・vanilla JS・データをすべて同梱し、外部ネットワークへの依存はない。フォントは OS 標準のスタックだけ）と `shots/*.png`。
- 題材: `tomasz-tomczyk/crit` @ `406875d`（v0.21.1）。地図・文書・出典・コード片はローカル clone から実測・抽出した。コード片 30 個（`SNIPS`）は実ファイルの該当行そのもの。修正デモの diff（`story_retries`）は実在の `generateStory`（`cmd/crit/cli_handlers_story.go:629-659`）に対して書いた妥当な提案で、行番号も実物に合わせた。
- 位置づけ: 実装（Svelte 5 SPA, D9）の前に、画面・状態・操作・数値表示の仕様を確定するための動くモック。外部とのやり取り（daemon・SSE・`claude -p`）はすべてクライアント内でシミュレートしている。

## 1. 開き方と状態の切り替え

`index.html` をブラウザで直接開く（`file://` で動く）。URL の hash で状態を決め打ちできる（スクリーンショットとレビューのため）。

| hash | 状態 |
|---|---|
| `#s=first-run` | 初回スキャン直後（0 tok）。見取り図 + 目次 + 見積りカード + facts |
| `#s=generating` | [生成] を押した直後から生成が進む様子（デモは約 40 倍速） |
| `#s=reader&room=session` | 生成済み。部屋「セッション状態」を選び、§6.4 をシートで読んでいる |
| `#s=reader&sec=s3a` | §3.1 を開き、その流れを見取り図に番号付きの矢印で重ねた状態 |
| `#s=composer` / `running` / `ready` / `accepted` | §6.6 の 1 文を選んで `f` → Composer → 実ステージの進行 → 提案（コード diff + 設計書 diff）→ 採用と Undo |
| `#s=inbox` | Inbox（状態 8 種、まとめて送る） |
| `#s=palette&q=mochikoshi` | ⌘K パレット（ローマ字で「持ち越し」を引く） |
| `#s=doc` | 文書ビュー（全文 + 縮図 + Code peek ペイン） |

追加の引数: `level=newcomer|standard|expert`、`theme=light|dark`、`lang=en`、`peek=<snip id>`（出典 peek を開く）、`gloss=<用語>`、`z=0..3`（地図のズーム段）、`clean=1`（プロトタイプ用ボタンを隠す）。画面右下の「PROTOTYPE · 状態 ⌘K」からも、⌘K の「デモ: …」で状態を移れる。

## 3. 見取り図（Floor plan）

### 3.1 何をどう描くか

| 要素 | 意味 | 元データ（本番） |
|---|---|---|
| 建物（太い外壁） | リポジトリ全体 | — |
| 区画（Z1 で太線の輪郭） | C4 の Container。crit では CLI（前面プロセス）/ daemon（`crit _serve`）/ 外部連携 / ブラウザ UI の 4 つ + ノイズ箱 | S3 の clustering + プロセス境界の静的検出（`main` パッケージ、`_serve` のようなサブコマンド、web 資産） |
| 部屋（壁 2px） | Component。パッケージのまとまり（crit は 17 部屋） | S3 の Leiden 結果（ディレクトリを初期値）。部屋あたりの表示名は L0 生成前は静的（パス）、生成後は LLM のラベル |
| 扉（隙間 + 点線の開き弧） | 隣り合う部屋の間に import がある | S2 の import グラフ。共有する壁が 34 単位以上あり、かつ import がある組だけ |
| 外部の人・物（建物の外のカード） | AI エージェント、人（ブラウザ）、`~/.crit/*`、GitHub/GitLab、crit-web、git | facts 検出（HTTP クライアント、`exec`、ファイル書き込み先）と README |
| ピン（しずく形・番号） | スレッド（コメント・AI 作業）。色と形で状態（朱 = 未解決、紫 = AI 作業中/提案、黄 = outdated、緑 = 解決） | `Anchor.diagram` |
| 点線の枠（紫・流れる） | AI がその部屋のコードを編集中 | job の `phase` イベント |
| 床の朱色の濃さ（オーバーレイ「変更頻度」） | 直近 41 commit で部屋に触れた commit 数（web 19、session 11、server 8 …） | `git log --name-only` |
| 黄の点線枠（「鮮度」） | 引用範囲が変わり、節が古い可能性 | anchor engine の stale 判定 |

### 3.2 ラベルは画面上で一定の大きさ（地図アプリ型）

- 壁・扉・矢印は `vector-effect: non-scaling-stroke` で線幅が一定。
- 部屋名などの文字は `translate(x y) scale(1/s)` で **画面上の px で描く**（`s` = 画面 px / 世界単位）。部屋の画面上の大きさ `sw × sh` で表示する情報を切り替える（判定は `applyCam()` で毎フレーム。17 部屋で 0.1ms 未満）。

| class | 条件 | 表示 |
|---|---|---|
| `xxs` | `sw < 34` または `sh < 20` | 何も出さない |
| `xs` | `sw < 92` または `sh < 48` | 短い名前だけ（`story`、`diff` など） |
| `sm` | `sw < 150` または `sh < 84` | 名前 + パス |
| `md` | それ以外 | 名前 + パス + 規模（files · 行 · test）+ 下端に状態行（確認済 n/m · 推測 k · 変更 c） |
| `lg` | `sw ≥ 330` かつ `sh ≥ 225` | md + **家具**（主なファイルと行数、主なシンボル）= Z3 コード段 |
| `sn`（追加） | 名前の推定幅 > `sw` | 長い名前の代わりに短い名前 |

### 3.3 意味のあるズーム（C4 の段と対応）

`k = s / s_fit`（`s_fit` = 見えている領域に建物がちょうど収まる倍率）で段を決める。

| 段 | 条件 | 見え方 |
|---|---|---|
| Z0 文脈 | `k < 0.62` | 建物は 1 つの箱「crit · Go 単一バイナリ · 20.8MB · 17 部屋 / 4 区画」。外部カードは外側へ広げ（画面 px で ±96/±64 ずらす）、建物との関係（`skill / hook`、`gh / glab`、`atomic write` …）をラベル付きで出す = System Context |
| Z1 区画 | `k < 0.9` | 部屋の壁を 16% に薄め、区画の輪郭を太線で描き、区画名と性質（「常駐 · 127.0.0.1 · HTTP / SSE · 状態」）を出す = Container |
| Z2 部屋 | 上記以外で `lg` の部屋が無い | 部屋名・パス・規模・扉 = Component（既定のホーム） |
| Z3 コード | 見えている部屋のどれかが `lg` | 部屋の中にファイルとシンボル = Code |

- 段の切り替えは不透明度の 0.2〜0.25 秒の遷移だけ（`prefers-reduced-motion` では即時）。HUD のボタン、`-` / `=`（§6.3 の「深さキー」）、ホイール、ピンチ（`ctrlKey` 付き wheel）で動く。カメラ移動は 300ms の ease-out（倍率は対数補間）。
- 部屋をクリック → 選択し、シートにその節を開き、隣接と依存の部屋以外の床を 50%（ダークは 72%）に落とし、**その部屋に出入りする依存だけ**を描く（段階的開示）。ダブルクリックか `Enter` → その部屋を Z3 まで寄せる。`Esc` → 1 段引く（シートが開いていれば先に閉じる）。

### 3.4 依存線の描き方（2 回目の反復で決めた）

最初は部屋の中心どうしを結んだが、選択した部屋の中心に線が集まり読めなかった（`shots` 初版）。次の規則に変えた。

1. **扉がある組**: 扉を横切る 68 単位の短い矢印だけを描き、ラベル（例 `Load · Subscribe`、`ComputeLineDiff`）を扉の脇に置く。
2. **扉がない組**: 両部屋の中心を結ぶ線分と各部屋の境界の交点から 14 単位内側を端点にし、長さの 18%（最大 40 単位）だけ膨らませた 2 次曲線で描く。矢印は終点に置く。
3. **リスクの辺**（例: `comment → session`「review.json を直接書く」= 1 秒 polling の件数ずれ）: 黄の破線。
4. **外部カードとの辺**: 既存の点線（カード → 外壁の扉）の上に矢印とラベル。

### 3.5 §3「主要な流れ」を地図に重ねる

§3.1 など流れの節を開くと、文書の手順番号と **同じ番号** の矢印を地図に描く（黒い角丸の番号札。ピンのしずく形と区別する）。往復（`cli → server` と `server → cli`）は互いに反対側へ膨らませ、短い組でも 70 単位以上離す。流れの表示中はピンと AI 枠を 28〜30% に薄める。

### 3.6 本番のレイアウト算出（プロトタイプは手配置。ここは提案）

- **floorplan layout**（ELK と同じ Bun Worker で実行）: (1) 建物 = 16:10 の長方形。(2) 区画を squarified treemap で分割。並びは「入口（エントリポイントを含む区画）を左上、UI を左下、外部 IO を右端」の決まった規則。(3) 区画の中を部屋で squarified treemap。部屋の面積は `clamp(a0·√LOC, Amin, Amax)` [仮]、並びは部屋の隣接行列の Fiedler ベクトル順（よく import し合う部屋が隣になり扉ができる）。(4) 扉 = 共有壁 ≥ 34 単位かつ import のある組の共有区間の中点。(5) 同じ入力からは必ず同じ結果（id で安定ソート）。LOC の変化が 20% 未満なら前回の並びを保ち、家具が動かないようにする [仮]。
- 測り方: コーパス 5 repo（flask, ripgrep, hono, excalidraw, fastapi）で (a) import 辺のうち扉になった割合（目標 ≥ 45% [仮]）、(b) 建物全体を収めたとき `md` 以上で表示できる部屋の割合（≥ 70% [仮]）、(c) 40 部屋で layout ≤ 30ms を記録する。

## 4. シート（その部屋の設計書）

- 見出し: 区画 › 部屋、`§6.4 セッション状態`、読了時間（和文 500 字/分）、`確認済 12/14`、`推測 2`、パス、鮮度（古い可能性があれば「この節だけ再生成 ≈4k」）。タブ: 設計書 / コード（ファイル・シンボル、0 tok）/ スレッド。
- 本文は 15px・行間 1.85・1 行 34 字前後（シート幅 600 − 余白 64）。`line-break: strict`、`text-autospace: normal`、`text-spacing-trim: trim-start`、見出しは `word-break: auto-phrase`。
- **読者レベル**は `READER_LEVEL_RULES`（`contracts/core.ts`）をそのまま CSS のクラス（`html.lv-*`）で適用する。切り替えは DOM を描き直さず、class の付け替え 1 回（実測 1.3〜2.9ms、style + layout 込み）。

| | 初めて | 標準 | 詳しい |
|---|---|---|---|
| L3（Deep Dive） | 隠して末尾に「詳しく（L3 · n）」チップ | 折りたたみ | 展開 |
| 出典 | 段落末に「出典 n」チップ（押すと文中に展開） | 文中に `watch.go:967` | `watch.go:967-995`（範囲付き）+ 行番号 |
| 用語の下線 | すべての出現 | 節ごとの初出だけ | なし（hover は有効） |
| なぜ？ボックス | 展開 | 折りたたみ | 折りたたみ |

- 利用者が開閉した Why / Deep Dive はその選択（`data-u`）を優先し、レベルを変えても保つ。
- **確認バッジ**: 確認済は文末の小さな緑のチェック（`L0 範囲 ✓ · L1 識別子 ✓ · L2 hash ✓` を title に）。推測は黄の「推測」ボタンで、押すと「確認済にする / AI に確かめさせる ≈2k / 専門家に聞く」。確認済にすると `確認済 by @satoki`（human-verified、再生成で保持）。`⌥` を押している間だけ、すべての出典を範囲付きで、確認済を文字付きで出す。
- **出典 peek**: チップに 200ms hover（用語は 300ms）で開く。シート内の出典は **地図の左上（シートの左隣、y=58px）に固定位置で出す**（2 回目の反復で決めた。最初はチップの下に出したため本文を覆い、次に縦中央に出したため選択中の部屋を覆った）。中身: パス·範囲·`正確 · tree-sitter`·blob、該当行（Go の簡易ハイライト）、`o` 固定 / `⇧O` エディタ / `y` リンク、引用元の節。WCAG 1.4.13: カードの上に移れる、`Esc` で閉じる、勝手に消えない（離れて 220ms 後に閉じる）。
- **読書パス**: 左の rail に進捗リング（`4/7` と次の節）、シート上端に帯（「この節はコースに含まれる / 寄り道中」と次へのリンク）、末尾に前後のページャ。コースは既存ブロックの選び直しなので追加 0 tok。

## 5. 依頼の流れ（選ぶ → c / e / f → Composer → 実ステージ → 提案 → ⌘Enter → 一度だけ光る + Undo）

1. **選ぶ**: 本文の文字列を選ぶと、選択範囲の上に黒い浮遊ツールバー（コメント `c` / 説明 `e` / 修正 `f` / プロンプトとしてコピー `p`）。選択は 1 ブロック内に限る。Composer を開いている間も **CSS Custom Highlight API**（`::highlight(mitori-quote)`）で引用部分を塗る（DOM を割らない）。選択がなければ `j/k` でフォーカス中のブロック、地図なら選択中の部屋（`Anchor.diagram`）が対象。
2. **Composer**（対象ブロックの直下に overlay で出す。後続の本文は動かない。開いたら必要なぶんだけシートを scroll し、Composer の分だけ `min-height` を足して下端まで見えるようにする）:
   - 意図チップ: 質問 `⌘1` / 修正 `⌘2` / 指摘 `⌘3` / メモ `⌘4`。キーで開いたときの既定は `c` = メモ、`e` = 質問、`f` = 修正（D19）。
   - 修正のときだけ 2 択（doc_edit の 2 択と同じ考え方）: 「コードをこの依頼に合わせる」/「設計書を直す（コードが正しい）」。
   - コンテキストチップ: 節（0.3k）、本文が引用している範囲（`chars / 2.3` で概算）、呼び出し元（symbol index から自動で 1 件）、関連（`config.go:59-70`）、提案だけ（点線: `ingest.go:146-172 0.7k`、押すと追加）。× で外すと見積りが即座に変わる（実測: ≈3.6k → ≈3.3k）。
   - 見積り行: `≈3.6k tok · API換算 $0.021 · 約 8 秒 · claude-sonnet-5-5 · patch`。色の帯は < 10k 灰 / 10–50k 藍 / 50–200k 琥珀 / > 200k 赤。hover で内訳（固定 0.8k は lean system prompt で cache 可、各チップ、本文、入力/出力の見込み、router の判定根拠「2 files · 58 行」、見積り精度 ±12%）。
   - 式（プロトタイプの値）: `in = 0.8 + Σchip + 本文字数×0.8/1000`（k tok）、`out = {change 1.2, question 0.6, review 1.0}`、`usd = in×0.0024 + out×0.0125`（Sonnet 5.5 の in $2 / out $10 に cache 書き込みぶんを足した概算）[仮]。本番は 04 §2.1 の係数と `usage` の EMA 補正で置き換え、`result` イベントとの差を ±12% 以内にする。
   - `Enter` は改行、`⌘Enter` で送信、`Esc` で閉じる（下書きは保存。確認ダイアログは出さない）。すべての keydown は `isComposing || keyCode === 229` で先に抜ける。
3. **楽観的カード**: 送信と同時に、同じ位置にジョブカードを出す（実測 24〜31ms、Playwright 経由）。部屋には紫の流れる点線枠とピン、ブロックには紫の左帯と淡い脈動、status bar に `◐ th_7k2 作業中`。
4. **実ステージ**（`JobPhase` に 1 対 1。偽の % バーは出さない）: スナップショット `refs/mitori/th_7k2/base · dirty 0` 290ms → コンテキスト束 `MBF/1 · 2.4k tok · 4 範囲` 40ms → 起動 `claude -p · --setting-sources "" · --strict-mcp-config` 1.8s → 読み取り（ファイル名）→ 計画 `patch/1 · 2 files · 5 hunks` → 編集（worktree に適用）→ 範囲検査 `2 files ⊂ WRITE · deny glob 0` → 検査 `gofmt -l` / `go vet` / `go test …`。各行に所要時間、最下行に最新イベントの tail（`Read internal/config/config.go`）、フッターに「通常 6–11 秒（同じ意図の過去 12 件 · p25–p75）· 読み続けて大丈夫です」と [中止]。
5. **提案（ready）**: カードに「何を・なぜ」3 行、gate チップ（`gofmt -l 0.1s` など、すべて ✓）、`コード +33 −19 · 2 ファイル · 設計書 2 ブロック（§6.6 · §6.10）`、実績 `入力 2.5k（キャッシュ 0.6k）· 出力 1.3k · $0.021 · 7.8 秒（API 5.1 秒）· 見積 ≈3.8k（−1%）· 5h 枠 +0.1%`。設計書側は該当ブロックを **提案モード**（削除 = 赤の取り消し線、挿入 = 緑の下線）で表示し、ブロックごとに採用 / 却下。タブ非表示中に ready になったら `document.title` を `(1) ✓ mitori — crit` にする。
6. **レビュー overlay**（`r`）: 地図の上（rail を自動で畳む）に unified diff。行番号 2 列、`+/−` の記号と左右の色帯（色だけに頼らない）、対になる `−/+` 行は共通の前後を除いた部分を `<mark>` で強調。ヘッダに影響する部屋の縮図（CLI 入口・設定を塗る）。
   - **フォーカス単位**: 最初のフォーカスは「提案全体」。`⌘Enter` = フォーカス中を採用、`⌘⌫` = 却下、`n` / `⇧N` = 次 / 前の hunk（フォーカスが hunk に移ると `⌘Enter` はその hunk だけ）、`⌥⌘Enter` = すべて採用。全 hunk が決まった時点で適用する。
7. **採用**: overlay を閉じ、設計書の 2 ブロックを書き換え、**1 回だけ**緑に光らせ（1.1s、reduced-motion では静的）、地図の該当部屋も 1 回光らせる。ブロックの下に履歴 `R1 AI 生成 → R2 AI 修正（th_7k2 · 採用: あなた）`、左帯は緑。トースト「採用しました · コード 2 ファイル（未 commit）· 設計書 2 ブロック · checkpoint `refs/mitori/cp/0007` [元に戻す ⌘Z]」を 10 秒（下端のバーが縮む）。`⌘Z` / ボタンで checkpoint から戻し、提案はレビュー待ちに戻る（D4）。
8. **説明（e）**: 同じカードで 回答中 → 回答（出典チップと確認バッジ付き）→ 「文書に追記（FAQ）」で文書に昇格。

## 6. 補助画面

### 6.1 深さキー `-` / `=` / `0`（地図と文書で同じ操作）

「深さ」は地図ではズーム段（Z0–Z3）、文書では読者レベル。どちらに効くかは **ポインタかフォーカスがある領域** で決め、status bar に `深さキー → 地図 / 文書` と常に出す（決定事項 K1）。シートを開いた直後は文書。

### 6.2 Inbox（`g i`）

- 並び: 「あなたの番」（あなた宛て ● / レビュー待ち ◆ / 失敗 ✕）→「AI が作業中」（作業中 ◐ / 待機 ○）→「要対応」（outdated ⚠）→「下書き」→「解決済み」✓。状態は記号 + 色 + ラベルの 3 重（WCAG 1.4.1）。
- 絞り込み: すべて / 作業中 / レビュー待ち / 失敗 / あなた宛て / outdated / 解決済み（件数付き）。`j/k` で移動、`h` で解決済みを隠す。
- 右の詳細: 状態、節・アンカー、「地図で見る」、タイムライン、状態ごとの操作（失敗: 再試行 / agent mode に昇格 ≈14k / プロンプトをコピー、待機: 「watch.go を th_5c0 が編集中のため待機 — 同じファイルに触るタスクは自動で直列」、outdated: 新しい位置を指定 / 元のスナップショット、提案: 要約・gate・実績・差分を見る・採用）。
- 下端の帯: 「下書きコメント 3 件 → 1 回の実行にまとめる ≈18k tok（別々だと ≈41k · 23k 節約）[まとめて送る ⇧F]」。

### 6.3 ⌘K パレット

- 索引: 用語（よみ）、節、部屋、シンボル（tree-sitter で正確）、スレッド、操作（説明・修正・コピー・書き出し・テーマ・言語・レベル・移動・デモ）。プロトタイプは 104 件。
- 照合（上から順に最初に当たったもので点数）: ラベルの部分一致（100 − 位置、先頭一致 +20）→ かな入力をよみに一致（85）→ **ローマ字** をよみのローマ字に一致（82）→ 関連語（`TAGS`: 節や シンボルに付けた用語のよみ・英語名）に一致（62）→ 補助行に一致（50）→ ラベルの fuzzy（30）。ローマ字は両側を `shi→si, chi→ti, tsu→tu, fu→hu, ji→zi, sha→sya, cha→tya, ja→zya, nn→n, ou→o` で正規化するので、`mochikoshi` でも `motikosi` でも `もちこし` でも「持ち越し」と §6.4 と `carryForwardComment` が出る。
- 表示: 入力が空なら「最近 2 件 + 提案」。結果はグループ見出し付き、一致部分に下線。`↑↓` / `Enter` / `Esc`、フォーカスは入力欄のまま（`aria-activedescendant`）。閉じたら元の要素にフォーカスを戻す（戻さないと単一キーのショートカットが入力欄に吸われる。テストで見つけた不具合）。照合 + 描画は 1 打鍵あたり平均 0.5ms（104 件）。

### 6.4 初回（0 tok）と生成

- 見取り図・目次・facts は LLM を呼ばずに出す。シート（420px）の順: 見出し「スキャン完了 · 0 tok · 1,219 files · 0.25 秒」→ **見積りカード** → S0〜S4 の所要時間 → 「静的に分かったこと」カード 6 枚（エントリポイント 3、HTTP ルート 62、環境変数 12（値は出さない）、CLI 26、Go テスト関数 2,709、TODO 6）→ facts の表。
- 見積りカード: 深さの 3 択（概要 ≈0.12M · $0.4 / **標準** ≈0.4M · $1.3 / 完全 ≈1.1M · $3.6）、エンジン（`claude-cli` / 自分のセッション（`mitori gen --prep` / `--ingest` のコマンドを表示）/ API key）、`標準: 約0.4M tok · API換算 $1.3 · 約6分` と内訳（並列 3、overview は `claude-opus-5-5` で 2.4 分のクリティカルパス、module は `claude-sonnet-5-5`、5h 枠 推定 +11%）、[生成]（1 クリック）、送信先とデータの扱いの 1 行開示。
- 生成中: 目次の各節が「≈3.0k」→ 紫の点滅 → 読了時間 に変わり、地図の部屋が淡く明滅し、シートに「n/25 節 · 消費 tok / ≈400k · 経過」と実行中 3 本・待機の一覧。生成中の部屋をクリックすると「先に生成（キューの先頭へ）」。完了で「0.41M tok · $1.36 · 6:02 · 見積 ≈0.40M（+3%）· 5 分コース →」。

## 8. 受け入れ基準（map-first を本番で実装するときの判定）

1. `mitori` 起動から 3 秒以内（100k LOC 以下）に、見取り図（区画・部屋・扉・外部カード）、目次、facts カード、見積りカードが表示され、それまでの LLM 呼び出しは 0 回である。
2. 見積りカードは「`<深さ>: 約<N>M tok · API換算 $<x> · 約<m>分`」の 1 行と [生成] を、1440×900 でスクロールせずに見せる。[生成] 以外の操作では何も送信しない。
3. 部屋のラベルは画面上で 13px（名前）/ 11px（パス）/ 10.5px（規模）に固定され、§3.2 の 6 クラスの条件で切り替わる。どのズームでも文字が部屋の外にはみ出さない（clip）。
4. ズーム段 Z0–Z3 は §3.3 の条件で決まり、HUD・`-`/`=`・ホイール・ピンチのどれでも同じ段に到達する。段の切り替えで DOM ノードを作り直さない（class の付け替えだけ）。
5. 部屋のクリックからシートの節が表示されるまで p95 ≤ 100ms、カメラ移動は 300ms 以内に終わり、reduced-motion では即時。
6. 選択した部屋の依存だけが §3.4 の規則で描かれ、扉のある依存は扉を横切る短い矢印になる。部屋の中心に 3 本以上の線が集まらない。
7. §3 の流れの節を開くと、文書の手順番号と同じ番号の矢印が地図に出て、ピンと区別できる形（角丸の番号札）である。
8. 読者レベルの切り替えは DOM を描き直さず、`READER_LEVEL_RULES` の 4 項目（L3・出典・下線・Why）と行番号が表のとおりに変わる。利用者が開閉した Why / Deep Dive は保たれる。
9. シート内の出典チップの peek は地図の左上に固定位置で出て、シートの本文と選択中の部屋を覆わない（1440×900、シート 600px）。peek は hover・focus・クリックのどれでも開け、`Esc` で閉じる。
10. 本文の選択 → `c`/`e`/`f` で 100ms 以内に Composer が対象ブロックの直下に出て、後続の本文の位置は変わらない。Composer 全体が見えるまで自動で scroll する。
11. コンテキストチップを外すと、見積り（tok · $ · 秒 · mode）が同じフレームで再計算される。Enter では送信されず、IME の変換中のキーはすべて無視される。
12. 送信から 100ms 以内にジョブカード・部屋の AI 枠・ピン・status bar の表示が揃い、以降の表示は実イベント（`JobPhase`）の到着順だけで進む。% バーと根拠のない残り時間は出さない。
13. 提案はコード diff（hunk 単位）と設計書の提案モード（ブロック単位）を同時に示し、gate の結果と実績（入力 / キャッシュ / 出力 / $ / 秒 / 見積との差）を必ず含む。
14. `⌘Enter` はフォーカス中の単位（最初は提案全体）を採用し、採用したブロックは 1 回だけ光り、10 秒の Undo トーストが出る。`⌘Z` で checkpoint から戻せる。
15. Inbox は §6.2 の 5 グループの順で並び、状態は記号・色・ラベルの 3 つで区別される。`j/k`・`h`・`⇧F` が効く。
16. ⌘K はローマ字（ヘボン式・訓令式のどちらでも）とかなで用語・節・シンボルを引け、閉じたあとフォーカスが元に戻る。
17. ライト / ダーク / システムを切り替えられ、どの状態でも本文のコントラストは 4.5:1 以上（ダークの本文 `#e7e9ed` / 背景 `#161920`）。
18. 820×1180 では地図が上、シートが下からの bottom sheet になり、地図の HUD とズーム段はシートに隠れない。
19. UI 文言は ja / en で同じキー集合を持ち（parity テスト）、en でも設計書本文は主言語のまま「ブロック単位で翻訳 ≈0.3k tok」を案内する（D5）。

## 9. 決定事項（この方向で決めたこと）

- **K1 深さキーは領域で切り替える**: `-`/`=`/`0` はポインタ・フォーカスのある側（地図 = ズーム段、文書 = 読者レベル）に効き、status bar に対象を出す。地図と文書を連動させる案（初めて = Z1 …）は段の数が合わない（4 対 3）ので採らない。
- **K2 シートは overlay**: grid の列にしない。地図の再レイアウトを避け、カメラを「見えている領域」に合わせる。
- **K3 ラベルは画面上で一定、線は non-scaling**、情報量は部屋の画面上の大きさで決める（§3.2）。
- **K4 依存は選択時だけ、扉は短い矢印**（§3.4）。常時表示はチップ「依存線」で opt-in。
- **K5 peek の定位置**: シート内の出典は地図の左上に固定で出す（§4）。文書ビューでは右の Code peek ペインに固定（`o`）。
- **K6 流れは地図に番号で重ねる**（§3.5）。§3 の各ジャーニーは「地図上の経路」として読める。
- **K7 ⌘Enter はフォーカス単位で採用**（§5-6）。最初のフォーカスは提案全体なので、1 回で全部採用できる。
- **K8 初回シートの順序**は「見積りカード → スキャンの所要時間 → facts カード → facts 表」。CTA と 0 tok の事実を最初の画面に収める。

## 10. 契約（`docs/design/contracts`）への変更提案

1. `DiagramKind` に `"floorplan"` を加える。`DiagramLayout` に `doors?: {a: string; b: string | null; orient: "v" | "h"; x: number; y: number; len: number}[]` と `groups?: {id: string; polygon: [number, number][]}[]`（区画の輪郭）を加える。§3.6 の floorplan layout の出力先。
2. `DiagramAnchor` に `pos?: {x: number; y: number}`（ノード矩形内の 0〜1 の相対位置）を加える。地図上のピンの位置を保存し、レイアウトが変わっても部屋の中の同じ場所に置くため。
3. `SectionView` に `mapFlow?: {from: string; to: string; step: number}[]` を加える（`from`/`to` は `MapView.diagram` のノード id）。§3 の流れを地図に重ねるため。代わりに `sequence` の `DiagramIR` を使う場合は、ノード id を `MapView` と同じ id 空間にする規約が必要。
4. `MapView.modules` の各要素に、家具（Z3）用の `topFiles: {path: RepoPath; loc: number; symbols: string[]}[]`（最大 5）を加える。0 tok で出せる。
5. `ui.ts` の `DEFAULT_KEYMAP` に `map.zoomIn` / `map.zoomOut`（`=` / `-`、scope `"map"`）を加え、`ShortcutScope` に `"map"` を加える。`level.*` と同じキーを scope で使い分ける（K1）。
6. `PaletteItem` に関連語 `t?: string[]`（用語の id）を加える。節やシンボルを用語のよみで引くため（§6.3）。
